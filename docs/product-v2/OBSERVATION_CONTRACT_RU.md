# Контракт наблюдения и черновика v2

**Статус политики завершения: `PENDING_OWNER_APPROVAL`.**

Это проект для отдельного утверждения владельцем продукта. Он задаёт точный предлагаемый набор ответов и поведение незавершённого наблюдения. Создание этого документа не утверждает новые обязательные поля, не меняет runtime, frozen Analysis/Safety, существующие validators, исторические данные или release gates. Независимая основа хранения может развиваться отдельно; подключать описанную ниже политику завершения к пользовательскому потоку до её утверждения нельзя.

Русские формулировки здесь объясняют поведение. Они не являются утверждёнными строками интерфейса или готовыми переводами для 31 локали.

## 1. Проверенные исходные ограничения

Аудит опирается на точные версии:

- Production main: `d57f7c4f3d7cb3285f7fecc2342842c8518198e1`.
- Защищённый source anchor и база проекта контракта: `db6920193fb76028947ce148cd8ed61c847c5c3d`, `baseline/public-on-offline-candidate-12` / `development/public-on` на момент исходного аудита.
- UX draft PR #8: `2edd56fb7761b50f52c2e074284830e46b9080eb`; это отдельный UX draft, который не был выпущен в production main.
- Frozen artifact: `browser-packaging/artifacts/analytics-v1.f1f975900faaa64649bcef42412c1856543c8716711d4119df9b964f4bf8c824.js` из anchor. SHA-256 в имени: `f1f975900faaa64649bcef42412c1856543c8716711d4119df9b964f4bf8c824`.

Frozen engine требует конечные числовые ratings в диапазоне 0–10 и `hours` в диапазоне 0–168. Для числовых ответов нет допустимого значения «пропущено»: `null`, пустая строка, отсутствующее свойство или новый enum не являются числовым ответом. Значения 0 и 5 являются содержательными ответами пользователя и не могут служить заглушками.

Все шесть полей RIS/CIE должны содержать непустой текст. В существующем frozen validator текстовые поля IEP/OOP допускают пустую строку. `evidence: []` допустим по типу, но означает `not_recorded`; `['insufficient']` означает явно заявленную недостаточность информации. `direction: 'unknown'` — предусмотренный ответ о неопределённости.

`intentional: 'yes'` требует непустой корректный RIS patch. Для `'no'` и `'unsure'` patch должен быть пустым. `'unsure'` сохраняет предусмотренную frozen engine границу сегмента и не заменяется на `'no'`.

**Черновик не является циклом.** Frozen `N_completed` проверяет structural/CIE/identity/revision, а `fullyValidCycleCount` отдельно проверяет все поля. Поэтому даже частично заполненную структурную запись нельзя временно помещать в `intent.cycles`: это уже может изменить аналитические счётчики. Черновики и их metadata не передаются frozen facade.

## 2. Предлагаемая политика завершения

Следующая таблица целиком имеет статус `PENDING_OWNER_APPROVAL`. Она не описывает уже введённое ограничение приложения.

Обязательный ответ должен быть явно дан пользователем в этом наблюдении и удовлетворять существующему диапазону или enum. Простое присутствие значения в объекте не доказывает, что пользователь его выбрал.

| Поле | Предлагаемая обязательность | Точная семантика ответа и пропуска |
| --- | --- | --- |
| `iep.desire` | Обязательно | Явная оценка 0–10. Пропуск не превращается в 0 или 5. |
| `iep.belief` | Обязательно | Явная оценка 0–10. |
| `iep.emotion` | Обязательно | Явный выбор одной существующей категории из совместимого с frozen dictionary каталога. Neutral и Other являются ответами, а не пропусками. Произвольная новая строка не подставляется вместо категории. |
| `iep.emotionIntensity` | Обязательно | Явная оценка 0–10, в том числе при Neutral/Other. Приложение не выводит интенсивность из категории эмоции. |
| `iep.frequency` | Обязательно | Явный выбор `freq0`…`freq5`. `freq0` означает отсутствие такой активности, а не отсутствие ответа. |
| `iep.mental` | Обязательно | Явная оценка 0–10. |
| `iep.practical` | Обязательно | Явная оценка 0–10. |
| `iep.hours` | Обязательно | Явное число 0–168. Ноль означает сознательно указанное отсутствие затраченного времени. Существующий UI использует шаг 0,25 часа; это не повод менять допустимость исторических чисел frozen engine. |
| `iep.actions` | Необязательно | Пользовательский текст; можно оставить без ответа или явно пропустить. В completed cycle отсутствие текста представлено `''`, без автоматически добавленного «Нет». |
| `oop.currentState` | Обязательно | Краткий непустой пользовательский текст о наблюдаемой ситуации. Пользователь может своими словами указать, что ситуация пока неизвестна; приложение не придумывает такое утверждение за него. |
| `oop.achievement` | Обязательно | Явная оценка 0–10. Нельзя автоматически сохранять начальный ноль. |
| `oop.events` | Необязательно | Пользовательский текст; можно оставить без ответа или явно пропустить. Пустота представлена `''` и не означает «изменений не было». |
| `oop.direction` | Обязательно | Явный выбор `toward`, `none`, `away`, `mixed` или `unknown`. `none` и `unknown` имеют разные значения; ни один вариант не выбирается за пользователя. |
| `oop.evidence` | Обязательно | Явно выбран хотя бы один существующий basis: `direct`, `documented`, `otherPerson`, `subjective`, `insufficient`, `other`. `insufficient` позволяет честно указать недостаток информации. Не заменять его другим основанием ради получения аналитического результата. |
| `oop.external` | Необязательно | Пользовательский текст; можно оставить без ответа или явно пропустить. `''` не является утверждением об отсутствии внешних факторов. |
| `intentional` | Обязательно | Явный выбор `yes`, `no` или `unsure`. При `yes` пользователь выбирает RIS dimensions и подтверждает непустые replacement texts. При `no`/`unsure` сохраняется `{}`. Пустое replacement text нельзя незаметно заменить старым CIE. |

Минимальная обязательная текстовая часть IEP/OOP — одно описание `oop.currentState`; `actions`, `events`, `external` остаются необязательными. Для optional fields не требуется дополнительный клик «Пропустить» ради завершения. Отсутствие ответа и явный пропуск различаются в metadata, но оба честно дают пустую строку для соответствующего optional legacy field.

Если пользователь пока не может дать обязательную числовую оценку, доступно сохранение черновика. Завершение с числовым «не знаю» потребовало бы отдельного изменения контракта; это не реализуется через вымышленный 0/5, строку или обход validator.

Исторические observations не проверяются ретроспективно по этой новой UX policy. Их literal values, IDs, порядок, timestamps и существующие аналитические ограничения сохраняются.

## 3. Статусы ответов и нетронутые controls

Draft хранит для поля отдельно значение и состояние `unanswered`, `answered` или `skipped`. Названия являются семантикой проекта, а не обязательным форматом runtime API.

- Новые числовые и категориальные ответы начинаются с `unanswered`; числовое значение отсутствует или равно `null` только внутри draft.
- `answered` устанавливается явным действием пользователя: числовым вводом, выбором значения или отдельным осмысленным подтверждением показанного значения.
- Фокус, рендер, восстановление draft, переход Next, изменение языка и простое наличие DOM value не устанавливают `answered`.
- `skipped` применим к необязательным полям. У required fields пропуск оставляет наблюдение незавершённым.
- Очистка обязательного ответа возвращает поле в `unanswered`; прежний confirmation не переживает удаление значения.
- Восстановление сохранённого draft восстанавливает и значения, и их статусы. Оно не превращает `unanswered` в `answered`.
- Для текста draft сохраняет введённое пользователем содержимое. Проверка непустоты может использовать trim для проверки, но не должна переписывать старые записи или брать пример из подсказки как ответ.
- Необязательное поле может остаться `unanswered` при завершении. Metadata не должно утверждать, что пользователь сознательно пропустил его, если такого действия не было.

HTML range может технически иметь thumb/value до взаимодействия. Это не ответ: интерфейс должен показывать отсутствие выбранного ответа и предоставлять доступный способ подтвердить именно показанное значение без обязательного движения шкалы. Альтернатива — изначально пустой numeric control. При разборе числового ввода пустота проверяется до преобразования: `Number('') === 0` не может создавать ответ.

Нельзя придумывать confirmation flags для импортированных исторических cycles. Нельзя менять frozen `defaultLike` или корректировать пользовательские значения, чтобы снять `POSSIBLE_UNREVIEWED_DEFAULTS`. Metadata приложения не даёт права отменить frozen limitation.

## 4. CIE первого и повторного наблюдения

### Первое наблюдение

После успешного сохранения нового RIS существует намерение, но ещё нет завершённого наблюдения. Первый draft получает буквальный снимок шести полей сохранённого RIS и ссылку на его версию/отпечаток.

Основной Continue на экране сохранённого RIS может одновременно означать явное принятие этого RIS как исходного CIE первого наблюдения, если это ясно объяснено пользователю. Должна быть возможность проверить все шесть полей. Тогда следующий экран — IEP, без повторного ручного заполнения RIS.

Save and finish later сохраняет намерение/черновик и не подтверждает за пользователя ещё не заданные ответы. Resume восстанавливает тот же draft. Если CIE уже подтверждён и не менялся, подтверждение сохраняется; если нет — пользователь подтверждает его при продолжении.

### Повторное наблюдение

Сохраняется различие между прошлой формулировкой и текущим самостоятельным описанием CIE: новый repeat draft не считает RIS либо CIE прошлого цикла автоматически подтверждёнными ответами. Предлагаемое исходное поведение — шесть пустых полей CIE, как в PR #8 для repeat flow. Next после заполнения подтверждает именно эти шесть значений.

Отдельное действие копирования текущего RIS в повторный CIE не утверждается этим документом: оно требует решения владельца о методике повторного опроса.

Любое редактирование подтверждённого CIE сбрасывает его acknowledgment. Если исходный RIS изменился в другом контексте после создания first draft, приложение не заменяет draft snapshot молча: требуется показать конфликт источника и получить новое осмысленное подтверждение. Старые CIE и завершённые cycles не переписываются.

## 5. Владение и сохранение draft

У draft есть стабильный `draftId`, ключ владельца `intentKey`, `kind: 'first' | 'progress'`, текущий шаг, CIE snapshot/acknowledgment, значения/статусы ответов и сведения о версии/времени сохранения. `first` обозначает первое наблюдение, `progress` — повторное. Эти сведения принадлежат новой модели приложения и не добавляют аналитических фактов.

`intentKey` — внутренний ключ независимого контейнера v2. Он не заменяет сохранённый legacy `intent.id`: исходный `intent.id`, в том числе пустой или совпадающий у разных импортированных намерений, сохраняется буквально и не используется как ключ владельца draft.

Предлагается один активный observation draft на намерение. Разные намерения могут независимо иметь свои drafts. Открытие Resume не создаёт новый draft и не переносит ответы из другого намерения.

| Действие | Предлагаемый результат |
| --- | --- |
| Сохранение RIS | Сначала надёжная запись намерения; ноль новых cycles. First draft создаётся/подготавливается в согласованной записи новой модели. |
| Ввод/выбор | Сохранение draft values и статусов; аналитика завершённых наблюдений не вызывается. |
| Next | Сохранение draft; после утверждения policy — проверка обязательных ответов текущего шага. При ошибке пользователь остаётся на шаге с введёнными данными. |
| Back | Сохранение текущих значений без требования закончить шаг, затем переход назад. |
| Save and finish later | Сохранение неполного draft и выход; history/cycle count не меняются. |
| Переход Home/History/к другому намерению | Сначала успешное сохранение текущего draft, затем переход. Ошибка сохранения не должна сопровождаться сообщением об успехе или молчаливой потерей ввода. |
| Закрытие wizard | По умолчанию сохранение и закрытие. Нейтральный выход не удаляет draft. |
| Cancel | Предлагается заменить неоднозначное действие явным сохранением и закрытием. Удаление draft — отдельное явно названное действие с подтверждением; этот документ не вводит его в UI. |
| Reload/повторное открытие приложения | Восстановление последней успешно записанной версии draft, шага, значений, статусов и CIE acknowledgment. |
| Storage/quota error | Старые persisted data остаются источником истины; ввод остаётся доступен на текущем экране, показано состояние «не сохранено» и возможность повторить запись. |

Перед программной навигацией запись должна завершиться успешно. Для browser Back приложение должно сохранять draft до собственного перехода либо использовать уже успешно сохранённую последнюю версию. Ввод желательно сохранять по мере изменения; отложенная запись должна быть завершена перед управляемым выходом.

**Нет обещания сохранности на unload.** Закрытие браузера, аварийное завершение, отключение питания и недоступное storage не гарантируют последнюю запись. `beforeunload`/`pagehide` не являются доказательством durability. Приложение может обещать восстановление только той версии, запись которой была подтверждена до выхода. Нельзя показывать «сохранено» на основании одного изменения объекта в памяти.

При конкурирующих вкладках более новая версия не перезаписывается молча: конфликт проверяется по версии записи и разрешается явно. При смене языка system copy перерисовывается, а literal user text и draft statuses не меняются.

## 6. Завершение и повторный запрос

Операция Complete после утверждения политики выполняет следующие действия как единое изменение committed model:

1. Проверяет принадлежность draft нужному намерению, актуальность версии и CIE acknowledgment.
2. Проверяет approved required-answer policy и неизменённые требования существующего legacy cycle shape/ranges/enums/revision pair. Policy приложения не подменяет frozen validators.
3. Создаёт один completed cycle из фактических ответов. Optional отсутствующий текст даёт `''`; обязательные отсутствующие числа не получают defaults.
4. Добавляет cycle только в историю его намерения и применяет подтверждённый intentional RIS patch, если `intentional=yes`.
5. В той же атомарной записи переводит draft в завершённое состояние/закрывает его. Только после подтверждённой записи обновляются UI и аналитическое committed input.

Для завершения используется стабильная связь draft и cycle ID либо сохранённая запись результата операции. Повторный клик, повторный callback, retry и reload после успешной записи возвращают уже созданный результат, а не добавляют второй cycle. Идентификатор операции нельзя генерировать заново при каждом retry.

Ошибка записи оставляет прежнюю историю/RIS и доступный draft. Нельзя сначала менять in-memory RIS/cycles, затем сообщать об ошибке, позволяя экспорту или аналитике увидеть неподтверждённый результат. После успешного commit и аварии до перерисовки повторное открытие видит завершённый cycle и не предлагает повторно завершать тот же draft.

Timestamp завершённой записи отражает фактическое завершение; время создания draft не выдаётся за время наблюдения. Корректность identity/chronology проверяется без вымышленных временных значений и без перестановки исторических cycles. Исходные timestamps импортированных данных сохраняются.
